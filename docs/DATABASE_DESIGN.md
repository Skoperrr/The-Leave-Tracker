# Database design — Phase 3 local implementation

The Prisma schema and initial SQL migration live in backend/prisma. Schema validation and client generation pass. PostgreSQL connectivity is verified, the initial migration has been applied and the three demo organisations plus annual/sick leave types have been persisted. Eight real-database tests passed using temporary records rolled back after each test.

One PostgreSQL database will contain User profiles linked by UUID to Supabase Auth, Organisation records and Membership joins. Unique (userId, organisationId) prevents duplicate membership. Roles and manager relationships belong to each membership, allowing Ayanda to belong to two organisations without granting either manager access to the other. A manager membership must reference the same organisation; this needs database constraints and service validation.

Organisation-scoped LeaveTypes define codes such as ANNUAL/SICK and whether balances apply. LeaveBalance allocations are unique by membership/type/policy year. LeaveRequests store date-only inclusive ranges, backend-calculated working days and PENDING/APPROVED/DECLINED/CANCELLED status. An optional LeaveGroup links organisation-specific child requests; a group does not authorise a global approval. A CalendarEvent uniquely references one approved request. AuditLogs record actor, organisation, action and time for decisions and admin changes.

Composite foreign keys constrain membership/type/manager/event references to the same organisation, and leave group/user ownership must match the request owner. Unique constraints prevent duplicate memberships, allocations and calendar events. Indexes cover membership, organisation, dates and statuses. Allocations use Decimal(8,2); requests store integer full working days. API services must serialise decimals into contract JSON numbers.

The migration also checks nonnegative allocations, positive request days, inclusive same-year date order, decision metadata, required decline comments and no self-management/self-decision. Row-level security is enabled on business tables with no browser policies; Supabase browser users must use the backend API. Backend connections require an appropriately privileged server-only database role. Real PostgreSQL tests verify RLS enablement, membership uniqueness, same-organisation manager/type references, nonnegative allocation, date-only persistence, date order and approval metadata. Remaining workflow invariants still need service and integration tests in later phases.

Demo policy: count inclusive weekdays, excluding Saturdays/Sundays. Public holidays and half days are not included in v1. Reject cross-year requests explicitly. Overlap checks consider PENDING and APPROVED requests for the same membership, allowing matching dates in different organisations. Remaining = allocated - approved - pending; approval transfers a reservation without another deduction. Decline/cancel releases it. Leave allocations are fictional demo policies, not South African legal guidance or official HR policies; choose and document the actual seed amounts in Phase 3.

Phase 5 locks selected membership rows in ID order with parameterised SELECT FOR UPDATE, then rechecks active user/membership/organisation, types, overlap and balances under READ COMMITTED. A simultaneous submission waits and sees the previous committed reservation. Children, group and submission audits commit together. Cancellation uses the same lock and guarded PENDING update with audit. Reads use REPEATABLE READ so allocations/status aggregates share a snapshot. Allocations stay unchanged; Decimal subtraction produces JSON day counts. Future approval/admin allocation services must follow the same lock convention.

Manager decisions now lock owner and actor memberships in global ID order, revalidate current authority/status and commit decision, audit and one calendar event together. Cancellation and submission share owner locking, so approval/cancellation cannot both win. Pending-to-approved moves usage buckets without reducing remaining twice. Decline releases pending usage. Calendar query selects only approved active events and omits notes/types. Unique requestId prevents duplicate calendar entries. Failure-injection tests verify status and audit rollback when event/audit writes fail. No new migration was needed for these workflows.

The baseline seed includes the three named organisations and six balance-limited types: annual, sick, family responsibility, maternity, parental and religious leave. The four additional types require explicit admin-assigned allowances; see [LEAVE_TYPES.md](LEAVE_TYPES.md). The separate Auth account seed now provisions Ayanda, Thabo, Lerato, Sibusiso, Naledi and Neo with real development Supabase Auth UUIDs, nine organisation memberships and eighteen 2026 allocations. Credentials are generated into an ignored owner-only local file and never printed. It reuses only marked fictional Auth accounts without resetting passwords or database administration changes. Annual=15 and sick=10 days are fictional assessment policy values. Requests in different statuses remain pending the leave-workflow milestone. See DEMO_ACCOUNTS.md.


## Implemented email/calendar extensions

Email signup creates only a verified Auth-ID User profile; memberships and leave allocations require separate organisation-admin assignment. No new password or signup-role tables are created. Google Calendar adds OrganisationCalendarIntegration, GoogleOAuthState, CalendarSyncJob and ExternalCalendarEvent. Each credential/worker mapping remains bound to its organisation through composite foreign keys; all four new tables have RLS without client policies. Refresh tokens and PKCE verifiers are AES-256-GCM encrypted with organisation/purpose/key-version associated data. State and browser nonce are hashed; state expires and is consumed atomically. CalendarEvent gains a positive revision and composite ID/organisation key. Canonical Google calendar IDs are unique across organisation connections, preventing alias reuse. Outbox uniqueness covers integration/event/configuration revision/event revision/operation; leases and attempts support restart/retry, with no Google network call inside approval transactions.
